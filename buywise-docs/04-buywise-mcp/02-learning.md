# buywise-mcp - Learning Notes

## Local end-to-end build (2026-10-30)
- **MCP** = a standard way to offer tools to an AI: each tool has a name, description and JSON input schema; the agent lists and calls them over HTTP.
- **Layout (ADR-031):** one process, one server per domain: `/mcp/catalog` (search_products, get_product), `/mcp/inventory` (list_stores, check_stock), `/mcp/orders` (list_my_orders, get_order, quote_order, place_order, cancel_order).
- **SDK v2:** `MCPServer` + `@server.tool()`; stateless streamable HTTP; tool errors raised as `ToolError` so the reason reaches the model.
- **Try:** `make -C buywise-mcp smoke`.

## Phase M step 1 - tool snapshots + integration tests (2026-11-22, ADR-064)
- **Why first:** every later Phase M step changes tools; tests must exist before the changes so each change is seen and checked.
- **Snapshot tests** (`tests/test_snapshots.py`, files in `tests/snapshots/{catalog,inventory,orders}.json`): the SDK `Client` connects to each `MCPServer` **in-process** (no HTTP) and lists tools, prompts, resources; the result must equal the file. A description is a prompt to the model, so any change shows up as a failing test and a git diff. After an intended change: `make -C buywise-mcp snapshots`, review the diff, commit.
- **Approach change (architect, same day):** the current MCP code is a prototype, not a base. Phase M rebuilds buywise-mcp to the M design (version 1); tests are written from the design, test-first. The first version of step 1 snapshotted today's 9 tools and had 11 tests of today's behaviour - both removed; the mechanism and the stack stay. A server without an approved snapshot is skipped until its M-design contract is reviewed.
- **Integration tests** (`tests/integration/`): Testcontainers starts Postgres (`pgvector/pgvector:pg17` + `buywise-db/database/01-databases.sh`) and `buywise-services:dev` on a private Docker network; Flyway runs on services start; the seed SQL from `buywise-db/services/02-dml` loads `03-data`; MCP runs in the test process on a free port; tools are called over Streamable HTTP like the agent does (`call(...)` fixture), and the database is checked directly (`stack.sql(...)`). `test_stack.py` checks the stack itself (services healthy, 50 products, 10 stores, orders, MCP up). ~8 s per run.
- **Services image** (`buywise-services/Dockerfile`, `make -C buywise-services image`): Java 25 JRE + the jar, non-root user; settings from environment variables. Reused for Kubernetes later.
- **Findings:** tools returning `dict` (get_product, check_stock, get_order, quote/place/cancel) send no structured result, only JSON text - list tools get `{"result": [...]}` automatically (fixed in step 2, ADR-054). Tool errors arrive as "Error executing tool <name>: <message>" text (typed in step 2, ADR-055).
- **Commands:** `make -C buywise-mcp test` (snapshots + lint), `make -C buywise-mcp snapshots`, `make -C buywise-mcp test-integration` (builds the image, runs the containers). CI job `mcp` runs both.

## Phase M step 2 - version 1 structure, typed results, typed errors (2026-11-22, ADR-054, ADR-055)
- **Structure:** `buywise_mcp/core/` (shared: `models.py` Money + strict base, `errors.py` typed errors, `services.py` client + circuit breaker, `identity.py` customer via `Resolve`), `buywise_mcp/domains/<domain>/` (`tools.py` = the server + its tools, `models.py` = its results), `config.py` (settings from env). `app.py` mounts the domain servers. The prototype `servers.py` / `services.py` are gone.
- **Typed results:** every tool returns a `ToolModel` (Pydantic, strict, immutable) -> the SDK generates `outputSchema` and sends `structuredContent`; the text the model reads is the same data as JSON. snake_case everywhere; money is a JSON number (`Money`: exact `Decimal` inside, rounded to cents); every result is an object (`{"products": [...]}`, not a bare list). Arguments use `Annotated[type, Field(description=...)]` so every argument is described for the model.
- **Typed errors:** `ToolFailure(code, message, retryable, hint)` raised anywhere -> `@typed_errors` returns `is_error: true` + structured `{code, message, retryable, hint}` + text "code: message Hint: ...". Per-tool hints (e.g. unknown SKU -> "Check each sku with get_product"). HTTP mapping in `core/services.py`: 400/422 invalid_input, 401 not_logged_in, 403 forbidden, 404 not_found, 409 conflict, 5xx/429/timeout unavailable + retryable (5xx detail never passed on). Any other exception -> logged, generic `unavailable`.
- **Circuit breaker:** closed -> 5 consecutive failures -> open (fail fast, no calls) -> after 10 s half-open (one trial) -> success closes / failure reopens. Business errors (4xx) do not count. MCP never retries.
- **Identity via `Resolve`:** `customer: Customer` in a tool's signature = filled by `current_customer` (header today, token in step 4), absent from the input schema. SDK lesson: an exception raised inside a resolver reaches the model only as plain text, so the resolver returns `Unresolved(...)` and the decorator turns it into the typed `not_logged_in` error.
- **Bugs found by the new tests:** stock "at every store" returned nothing (an empty `storeId=` matched no store - also in the prototype); an unknown store answered "0 in stock" (now `not_found`).
- **Also changed:** services message "Unknown SKU X" no longer carries an AI hint (MCP adds it); the agent reads `structured_content` (product cards, order confirmation) instead of parsing text, and no longer calls services directly (store names come in MCP results; the store list via `list_stores`).
- **Tests:** `test_errors.py` (mapping, no leaks, breaker states with a fake clock, decorator), `test_tool_rules.py` (every tool: real description, object result, strict schema, described arguments, no customer argument, snake_case, money = number), integration `test_catalog_inventory.py` + `test_orders.py` (27 tests; every result validated against its output schema, every error against the error shape). Snapshots in `tests/snapshots/` = the version 1 contract after the architect's review.
